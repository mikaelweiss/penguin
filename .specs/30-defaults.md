# Catalog

The engine package (`@mikaelweiss/penguin-engine`) carries an `examples/` directory. That directory is the starter catalog. Install enables it with one line, `starter`, in `~/.penguin/catalogs`. penguin reads the files from `examples/` itself. It does not copy them into the home.

- `examples/adapters/claude.ts`: the `agent` role on the claude CLI: sessions over `--session-id` and `--resume`, stream-json into typed agent events (text, thinking, and each tool call with what it acts on), results over `--json-schema`, and `--permission-mode` at `acceptEdits`, which a `permission` session option overrides. A run has nobody to ask, so a denied edit costs the whole turn.
- `examples/adapters/codex.ts`: the `agent` role on the codex CLI: one codex thread per penguin session, started on the first turn and resumed by id after, the `--json` stream into typed agent events (text, thinking, and each tool call with what it acts on), results over `--output-schema`, and the model and the sandbox mode as `-c` overrides.
- `examples/adapters/cursor.ts`: the `agent` role on the cursor-agent CLI: one cursor chat per penguin session, opened by the first turn and resumed after with the chat id the stream reports, `cursor-agent -p --force` with the stream-json events into typed agent events (text, and each tool call with what it acts on), results as one JSON object read out of the final text.
- `examples/adapters/opencode.ts`: the `agent` role on the opencode CLI: `run --format json` with the prompt on stdin, its line-delimited events into typed agent events (text, each tool call with what it acts on, and reasoning when the user turns thinking on), and sessions over `--session`. opencode names its own session, so the first turn of a handle reads the id off the event stream and later turns resume it. A turn that finds no id opens a session instead of failing, which is what a retry of a failed first turn needs. The CLI takes no schema, so a typed result is asked for in the prompt and read back out of the reply. The last block that parses is the result, because a reply often shows an example before the answer.
- `examples/adapters/pi.ts`: the `agent` role on the pi CLI: sessions over `--session-id` on every turn, `--mode json` wire events into typed agent events (text, thinking, and each tool call with what it acts on), results over a `penguin_result` tool that a per-turn extension file registers.
- `examples/adapters/git.ts`: the `vcs` role on git: staging, commits, pushing a branch to origin, worktrees, what the tree and the head hold, fetching a ref, pulling a fetched ref into a working tree, rebasing a branch onto a ref, and merging one branch into the checked-out one. A rebase call reports the files it stopped on, so the workflow drives the resolution and the continue. Every worktree sits under the run state root, one folder per repository name, on a branch named for the worktree. A worktree whose path is taken is reported, never overwritten, and a forced removal deletes a path git refuses to remove.
- `examples/adapters/gh.ts`: the `github` role on the gh CLI: read an issue or a pull request and its comments, create, diff, comment on, and approve pull requests, watch one pull request as a subscription of typed changes, the merge queue among them, and watch the pull requests that ask for one reviewer's review as a subscription of the fresh requests. Every call runs through one helper that holds what a person can fix at a gate and calls again: gh absent, gh signed out, and no git remote. Pushing the branch is the `vcs` role's work, so no gate asks a person for it. The gate offers done and skip, and skipping gives the workflow the failure. Creating the pull request for a branch that has one already answers with the open one, marked `existed`, so a second run picks the review up instead of stopping.
- `examples/adapters/jira.ts`: the `jira` role on the Jira Cloud REST API: read an issue and its comments, and search, create, comment on, and transition issues, under a token penguin asks for once (`20-architecture.md`, credentials).
- `examples/workflows/ship.ts`: a ticket to open PR pipeline: it calls work, then open-pr.
- `examples/workflows/ship-local.ts`: a ticket to landed commit pipeline: it calls work, commits, then holds at a gate until the user answers done or asks for a change, and lands the branch with land.
- `examples/workflows/work.ts`: the shared middle of both pipelines: triage the ticket, name the branch in an agent turn that reads the ticket and what triage found, hold the work in a worktree on that branch, read the baseline on that fresh worktree, then plan and implement each task against it. The workflow reduces the answered name to what git takes, so a name the agent styles freely still cuts a worktree. Each task commits once its review round ends, then holds at a gate. The user tries the change and answers done, or says what to change, which implements and commits again. The next task starts on work the user has seen. The worktree's head sha and the baseline gates travel to every review.
- `examples/workflows/triage.ts`: the triage loop: is the ticket ready to work on, the deciding fact, the tasks that build it, and what the reading found. It reads the ticket to text first (`helpers/ticket.ts`). Questions gate to the user first, and a split into more than one task holds at a gate that approves the split or takes a revision. The reading travels to the planner, so one ticket costs one pass over the files.
- `examples/workflows/plan.ts`: the plan loop: questions gate to the user first, then the plan holds at a gate that approves it or takes a revision, and a revision answer feeds back to the planner. It reads the ticket to text first (`helpers/ticket.ts`). What triage read arrives as context the planner starts from.
- `examples/helpers/ticket.ts`: reads a ticket reference to text for triage and plan. A Jira key or a GitHub issue number is fetched with its comments, and anything else is the text itself.
- `examples/workflows/implement.ts`: a persistent implementer and a persistent reviewer, both across every round, so the second round reads the new diff and not the whole tree again. The blocking findings of a round brief the next one, and a `rounds` bound ends the loop.
- `examples/workflows/review.ts`: one review turn of a working tree against its acceptance checks, the base commit to diff against, the baseline gates, and the blocking findings so far. The verdict follows the blocking findings alone: a note never holds up a change.
- `examples/workflows/baseline.ts`: one turn on a fresh worktree that records what each quality gate says before any change. Every later review reads it instead of proving the same failure again.
- `examples/workflows/commit.ts`: one commit: the message is an agent turn, and the staging and the commit are engine calls. A tree with nothing to commit reports it and writes nothing.
- `examples/workflows/land.ts`: the rebase loop, over one ref. It gates first when the checkout is on some other branch. Each pass fetches the target, fast-forwards the checked-out target to `origin/`, rebases the branch onto that same target, and gives each conflict to an agent, up to a `resolutions` bound. The rebase target and the fast-forward target are one branch, so a target ahead of origin still lands. A target that diverged from origin gates instead. A pass that conflicted repeats, up to a `passes` bound, so the branch lands on a target nothing moved under it. Then the target fast-forwards to the branch, which keeps the history linear, and the worktree the branch was built in comes off.
- `examples/workflows/open-pr.ts`: commit, push, the pull request, then a gate loop that runs address-feedback until the user answers done. Each round of feedback commits and pushes the same way, so the pull request always reads what the agent wrote. A branch that never reaches the remote holds at a gate instead. A pull request that was open already is the answer, not a failure, and takes the same loop.
- `examples/workflows/review-pr.ts`: a review of an open pull request that follows it until it closes: a triage turn over the PR diff first, which holds a change small enough to read at a gate where the user keeps it or asks for the review, a worktree on the PR head, a gate to use, replace, or exit when that path is already taken, an agent review fed the PR conversation and interrupted with changes as they land, findings as blockers and non-blockers, a gate on blockers, the feedback posted as a comment, an approve when nothing blocks, and a fresh review round on every push. A draft PR waits, a queued PR waits until it leaves the merge queue, and previous findings feed each new round. The triage comes before the worktree, so a PR the user keeps costs no checkout.
- `examples/workflows/pr-queue.ts`: the review queue: it watches the pull requests of the repository the run started in that ask for one reviewer's review, and it calls review-pr on each one as it arrives. A review lives until its pull request closes, so the reviews run beside the watch and beside each other. A pull request already under review never starts a second one. A draft pull request is no request until it is ready. The run ends when the user stops it.
- `examples/workflows/make-workflow.ts`: an idea to a new workflow: a design held at an approval gate, then a write-and-review loop with a `rounds` bound, into the home or the project.
- `examples/skills/`: the step skills, one directory each, in the Agent Skills format (`20-architecture.md`, skills): `penguin-triage`, `penguin-branch`, `penguin-plan`, `penguin-baseline`, `penguin-implement`, `penguin-review`, `penguin-commit`, `penguin-resolve-conflicts`, `penguin-triage-pr`, `penguin-review-pr`, `penguin-address-feedback`, `penguin-design-workflow`, `penguin-write-workflow`, `penguin-review-workflow`. The `penguin-` prefix keeps them clear of the skills `pn sync-skills` links in.
- `examples/defaults`: the role choices the catalog ships, one line, `agent claude`. More than one agent adapter arrives together, and this line says which one a run takes (`20-architecture.md`, adapters). Install writes it into a fresh home.
- `examples/tsconfig.json`: maps `penguin` to the installed CLI package and `zod` to the engine package for editor types, and includes the workflows, the helpers, the adapters, and the generated `penguin-env.d.ts`. Install copies this file into a fresh home so personal workflow files typecheck.
- `examples/penguin-env.d.ts`: the generated ctx types for the shipped adapters. penguin rewrites it after install (`20-architecture.md`, storage).

The big workflows call the small ones (`10-workflow-model.md`, composition), and every workflow also runs alone. The name says which is which: a step is one bare verb (`plan`, `baseline`, `implement`, `review`, `commit`, `land`, `triage`, `work`), and a pipeline is a compound or an outcome (`ship`, `ship-local`, `open-pr`, `review-pr`, `pr-queue`, `make-workflow`).

Personal workflow ideas live in `WORKFLOWS.md`, not here.
