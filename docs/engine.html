The connective tissue

The engine

Four jobs, and any feature that needs a fifth is either a new adapter, a new workflow, or out of scope.

🗂️ 1 · Catalog

Find workflow and adapter files across catalog directories. Listing and loading is not executing.

🔧 2 · Ctx

Validate params and wire installed adapter roles onto ctx, resolving which implementation fills each role.

🖥️ 3 · Process

Own the run's working directory and the processes it spawns, through the Host an adapter builds against.

🧾 4 · Trace

Append each adapter call and outcome to a log, for debugging a run after the fact.

What the engine does NOT do

It does not route messages, hold state machines, retry agent turns, render anything, or know one adapter role from another. Those all live in workflows and adapters.

1 · Catalog: where definitions live

The project, the home, and enabled catalogs are one ordered scan. Earlier wins.

2 · Ctx: resolving a role to one implementation

Each role on ctx needs exactly one implementation. pick in catalog/adapters.ts decides.

3 · Process: the host

The engine owns the run's working directory and every process it spawns.

createHost(cwd) in host.ts is the only thing that touches the operating system. It hands each adapter a Host with four fields, and nothing else:

FieldWhat it is
cwdThe run's invoking folder. Relative cwd options resolve against it.
statepenguin's state folder, where an adapter keeps what survives between runs.
shell(cmd)Run a shell line, buffer stdout and stderr, resolve to { code, stdout, stderr }.
exec(argv)Spawn an argv directly, stream output back through onOutput, resolve to an exit code.

The split matters: shell is for a command whose whole output you want at the end (a git status); exec is for a long-running process you want to watch as it goes (an agent turn streaming JSON).

4 · Trace

The engine appends each adapter call and its outcome to a log. It is a debugging record of what a run did, not a replay journal: the world is the state store, and a workflow's own checks decide what to redo.

Loading a definition file

Definition files import penguin and zod bare, with no install of their own.

A workflow or adapter file starts with import { workflow } from "penguin" and import { z } from "zod". Those packages are not in the file's own folder. The loader in catalog/loader.ts registers a Bun plugin that serves both names from penguin's own copies, which also live inside a compiled binary, never on disk.

// catalog/loader.ts - virtual modules for bare imports
Bun.plugin({
  name: "penguin-definitions",
  setup(build) {
    build.module("penguin", async () => ({
      exports: { ...(await import("../core/index.ts")) },
      loader: "object",
    }));
    build.module("zod", () => ({ exports: { ...zod }, loader: "object" }));
  },
});

Loading then validates the shape: load rejects a file that does not default-export a workflow with a run, a params schema, and a description; loadAdapter rejects one missing a role, name, description, or build. A bad definition fails at load, not mid-run.
