Workflows

A workflow is a plain object with three fields: a one line description, a Zod schema for its params, and run(ctx). Put a .ts file in a catalog's workflows/ folder, default-export a workflow(...), and it is findable. 

import { workflow } from "penguin";
import { z } from "zod";

export default workflow({
  description: "what this does, one line",
  params: z.object({}),

  async run({ vcs, view }) {
    const state = await vcs.dirty();
    await view.show(state.dirty ? "tree is dirty" : "tree is clean");
    return { dirty: state.dirty };
  },
});

Destructure only the roles you use. That line is documentation: it says which parts of the world this workflow can touch.

workflow() is an identity function with two checks, both about what a person reads. It throws PenguinError when the description is missing or blank, and when a param carries neither a .describe() line nor .meta({ internal: true }).

ctx

export type Ctx<Params> = { params: Params } & Adapters;

ctx is the validated params plus one entry per installed adapter role, and nothing else. Adapters is an empty interface that a catalog widens by declaration merging. In the starter catalog that happens in examples/penguin-env.d.ts, which is maintained by hand: 

declare module "penguin" {
  interface Adapters {
    agent: ReturnType<(typeof claude)["build"]>;
    github: ReturnType<(typeof gh)["build"]>;
    jira: ReturnType<(typeof jira)["build"]>;
    vcs: ReturnType<(typeof git)["build"]>;
    view: View;
  }
}

What a workflow may not do

  • Print. Output goes through view.show.
  • Parse argv or read environment variables. Input arrives as params.
  • Spawn a process or read a file. That is an adapter's job, through host.
  • Reach an adapter that is not on ctx.

Nothing enforces this at runtime. It is a discipline, and it is the payoff: a workflow that touches the world only through ctx reads and tests as one function.

Talking to a person

await view.show("staged 3 files");
const branch = await view.ask("Which branch?", z.string());

show sends something to whoever is watching. ask sends a question and resolves when they answer, validated against the shape when you pass one. Without a shape you get the raw string.

The shape is the whole input system. A frontend renders whatever control fits it, and the workflow just gets a typed value: 

z.string()                      // free text
z.boolean()                     // yes or no
z.enum(["ship", "hold"])        // pick one
z.array(z.enum(["a", "b"]))     // pick many
z.object({ title: z.string(), urgent: z.boolean() })  // a form

The terminal frontend parses a typed answer from the typed line, JSON included. A richer frontend renders buttons, toggles, and multi-selects from the same shape, which the run file records as JSON Schema. No workflow changes between them.

Free text goes to an agent

A union of an enum with z.string() puts the choices and a text box in front of the person at once: 

z.union([z.enum(["go", "skip"]), z.string()])

Reach for it only where the workflow hands that text to the agent that just stopped, as its next instruction. The text box is a promise that words will be read. A gate that acts on the named choices and drops everything else asks the same question again, which reads as a dead key. Where no agent is waiting to take the words, name the choices and let the person pick.

Params a person answers

A launch form is built from the params schema, so the schema decides what a person is asked. Every param they fill carries a one-line .describe(), which is the only label the form has to show. A param that only a calling workflow ever fills carries .meta({ internal: true }) instead, which keeps it off the form while call still passes it: 

params: z.object({
  task: z.string().describe("the change to make"),
  baseline: z.string().default("").meta({ internal: true }),
})

Those two markers are exhaustive for whether a param is shown: one with neither refuses to load, so a form can never show a person a box nobody can label.

A param that holds prose rather than a word carries .meta({ multiline: true }). It changes nothing about whether the param is shown or what the workflow receives, only how the box is drawn: one that wraps and grows instead of a line that scrolls sideways. 

ticket: z.string().describe("the ticket to work").meta({ multiline: true }),

Each call is its own request with its own response. There is no inbox and no message router. An answer reaches its asker because the asker is the one awaiting it, so two parallel branches asking at once are two pending promises.

How a view talks to its frontend is that implementation's business. A terminal, a file, a socket, a web page, a Slack thread: all of them satisfy the same two functions, and no workflow changes when you swap one for another.

Awaiting view.ask is also how a workflow pauses. Whether a run is done or waiting on you is a fact about the code, not something you learn by scrolling. 

const answer = await view.ask(`Push ${head.branch} to origin?`, z.enum(["yes", "no"]));
if (answer === "no") return { ...done, pushed: false };

Hearing from a person

ask is the workflow talking first. view.listen() is the other direction: an async stream of messages a person sends without being asked. It is the same shape as any other outside stream, a GitHub watch, a Slack thread, and the same rules apply: calling listen is opting in, each stream is private to its caller, and a workflow that never calls it accepts nothing. There is no inbox. A message reaches its listener because the listener holds the iterator.

The usual use is steering: race the stream against a running agent turn, and act when a message wins. The whole pattern is one race: 

const messages = view.listen()[Symbol.asyncIterator]();
const heard = await Promise.race([
  turn.value.then(() => undefined, () => undefined),
  messages.next().then((result) => (result.done === true ? undefined : result.value)),
]);
await messages.return?.(undefined);

if (heard !== undefined) {
  await agent.stop(session);
  await view.show(`stopped: ${heard.text}`);
}

Close the iterator when you stop caring, the messages.return line, so the view can tell its frontend the workflow is no longer listening.

Handle every adapter result

Adapter calls answer with data, not exceptions, so an unchecked ok is a bug you find later. examples/workflows/commit.ts leaves early on every branch, and every early return has the same shape as the successful one, so a caller can spread the result without asking which path produced it: 

const state = await vcs.dirty();
if (!state.ok) {
  await view.show(`commit failed: ${state.reason}`);
  return { ok: false, committed: false, message: "", reason: state.reason };
}
if (!state.dirty) {
  await view.show("nothing to commit");
  return { ok: true, committed: false, message: "", reason: state.reason };
}

Keep return values JSON-serializable. A frontend other than a terminal has to show them.

Compose instead of growing

When a workflow gets long, the fix is another workflow. call parses the child's params and runs it as a run of its own: a new process, a new run folder, its own line in any frontend's tree. 

const done = await call(ctx, commit, {});

The child builds its own adapters and gets its own params. Because it is a process, it can be stopped without touching its parent, and it can die without taking the parent down. The parent sees each of those as a typed rejection: RunStopped when a person or a parent stopped it, RunCrashed when the process died without recording an outcome, and a plain error carrying the child's message when the child threw. A parent that wants to survive wraps the call in try/catch; one that does not care rejects too, which is the right default. call needs the whole ctx, so a workflow that composes takes ctx as one argument and destructures inside: 

async run(ctx) {
  const { params, vcs, view } = ctx;
  const done = await call(ctx, commit, {});
  if (!done.committed) return { ...done, pushed: false };
}

A child works in its parent's folder unless the call names another one. That is call's fourth argument, not a param, so no workflow carries a folder in its schema and no launch form ever asks for a path: 

await call(ctx, commit, {}, { cwd: worktree });

Parallel children are Promise.all over call: 

const results = await Promise.all(
  params.dirs.map(async (dir) => ({
    dir,
    done: await call(ctx, commit, {}, { cwd: dir }),
  })),
);

A child can also run beside its parent instead of in front of it: examples/workflows/pr-queue.ts starts a review-pr child for each arriving review request and goes straight back to watching. Every child is its own lane for free. The parent's run file records which children it started, each child's file records its own story, and the tree a frontend draws is that parent chain. Nothing is announced to a UI and no scoping is threaded through ctx: the structure a person navigates is the file system's, and it is the same tree for the terminal, the desktop app, and anything else that reads the run folders.

Resuming is running it again

Penguin has no journal, no replay, and no checkpoints. A workflow inspects the world through adapters before acting, and acts only on what is missing. The world is the state store.

Kill commit anywhere and run it again. If the commit landed, the tree is clean and the second run does nothing. If it did not, the tree is still dirty and the second run finishes the job. No bookkeeping was needed to know which.

Every step that changes something outside gets the same three parts.

  1. Ask the adapter what is true now.
  2. Return early, with a full result, when the work is already done.
  3. Otherwise act, and report what the adapter answered.

open-pr does this across a composition boundary. Before it sends anything it calls commit, which reconciles itself against the tree, so a send after an edit or a crash picks up exactly what is missing: 

async function delivered(): Promise<boolean> {
  for (;;) {
    const wrote = await call(ctx, commit, {});
    if (wrote.ok) break;
    if (!(await again(`The commit failed: ${wrote.reason}`))) return false;
  }
  return pushed();
}

A journal has to be right about the outside world, and it never stays right. The commit that landed after the process died, the branch someone else pushed, the file a person edited by hand: all of it goes stale in a journal and none of it bothers a workflow that asks first. Resume respects this: replay only hands back what the run already saw and acted on, and everything after the first new call runs live, asking the world again.

Writing prompts

The reusable instructions live in a skill, and the turn names it: agent.turn(session, { skill: "commit" }, ...). The workflow file keeps only the runtime part of the prompt and the schema the answer fills. skills/commit/SKILL.md is a numbered procedure that says what to read, what to decide, and what not to do:

Do not stage the files. Do not commit. penguin does both after you answer.

The agent picks, the workflow acts. Letting the agent run git commit itself would move a deterministic step back into prose.

Run it

bun packages/engine/examples/run.ts \
  packages/engine/examples/workflows/commit.ts '{"dir":"."}'

The second argument is JSON, parsed and then validated against your params schema. Leave it off and the schema is parsed against {}, which succeeds when every field is optional. The starter catalog installs five agent adapters, so pick one first: write agent claude to ~/.penguin/config.
