One run, traced

Everything else in these docs describes structure. This page follows one command through the code in the order it actually happens, because the motion is what makes the structure make sense. 

bun packages/engine/examples/run.ts \
  packages/engine/examples/workflows/commit.ts '{"dir":"."}'

1. The frontend hands over

examples/run.ts reads two argv entries, parses the JSON, claims a run id, and calls the engine's run(file, params, options) from src/run.ts. From here on it is a frontend like any other: it tails the run's files and writes its inbox. Everything after this line is the same for a terminal, a UI, or a daemon.

2. The engine loads the workflow

run calls load(file) in src/catalog/loader.ts. The loader registers a Bun plugin (once per process) that serves penguin and zod as virtual modules, imports the file, and duck-types the default export: it must have a description, a params schema, and run. A file that does not fit throws PenguinError naming the file.

3. Params are validated

definition.params.parse(params) runs the workflow's own Zod schema over the JSON from argv. {"dir":"."} fits z.object({ dir: z.string().optional() }), so the run continues. A wrong shape throws here, before anything touches the world.

4. A host is made, adapters are built onto ctx

createHost(cwd, run) in src/host.ts is the only place processes come from: shell and exec, plus the cwd, home, and state folders, the run's own id and folder, and config(key) for ~/.penguin/config. Then run scans the catalogs for adapters, and for each role calls pick: one implementation wins, a builtin yields to anything installed over it, and a missing or ambiguous role throws with the fix in the message. Each winner's build(host) makes the API that lands on ctx under its role: ctx.vcs, ctx.agent, ctx.view.

5. The run file starts

Before the workflow sees them, each adapter is wrapped by src/trace.ts: a head line with the run's id, pid, workflow, params, git root, and parent opens ~/.local/state/penguin/runs/<id>/run.jsonl, then every call appends a pending line when it starts and an outcome line when it settles. The workflow never knows. This file is the run's whole story: frontends render it live, and when a run surprises you it is the answer to "what did it actually do".

6. The workflow runs

commit.ts now executes, top to bottom, touching the world only through ctx:

  1. vcs.dirty() asks git whether there is anything to commit. A clean tree returns early with a full result. This is the reconciler pattern: inspect first, act on what is missing.
  2. agent.open() makes a session, agent.turn(session, { skill: "commit" }, { result: Commit }) loads the commit skill's instructions, starts the claude CLI as a child process, and returns a handle: output, a stream of chunks, and value, a promise of the schema-checked result.
  3. The workflow forwards chunks it chooses to view.show. Nothing reaches a person unless this loop sends it.
  4. await turn.value is the typed answer: which files, what message. The adapter already retried once on a malformed result and validated the shape.
  5. vcs.stage(files) then vcs.commit(message) act on the answer. The agent proposed; the workflow performs the deterministic steps itself.

7. The result comes back out

run notes the outcome in the run file and returns the workflow's return value to the frontend, which prints it as JSON and exits. The commit is in git, the story of the run is in its file, and whatever a person saw went through view.

That is the entire machine. Two definitions, one wiring function, one process per run, one file per run.
