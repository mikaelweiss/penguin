The engine

The engine does three things every time a workflow runs.

Job Means Code
Catalog Find workflow and adapter files across catalog directories src/catalog/
Ctx Validate params and wire installed adapter roles onto ctx src/core/workflow.ts
Process Own the run's working directory and the processes it spawns src/host.ts

A fourth job, appending each adapter call to a trace log for debugging, is described in src/core/README.md and has no implementation in the package.

What it refuses

  • It does not route messages. A promise already goes back to its caller.
  • It does not hold state machines. A workflow is TypeScript control flow.
  • It does not retry agent turns. The agent adapter does, because retry is CLI-shaped.
  • It does not render anything. The view adapter does.
  • It does not know one adapter role from another. vcs, agent, and view are strings to it. It builds every installed adapter against the same host and puts the result on ctx under its role, with no idea that view is special.

The test for a new feature. If a proposal needs a fourth engine job, a new base class, or a new lifecycle hook, it is in the wrong place. It is either a new adapter, a new workflow, or out of scope.

The whole runtime path

packages/engine/examples/run.ts is a frontend in thirty lines.

const definition = await load(file);
const params: unknown = definition.params.parse(json === undefined ? {} : JSON.parse(json));
const host = createHost(process.cwd());
const ctx: Record<string, unknown> = { params };
for (const entry of await installedIn([starterCatalog()])) {
  ctx[entry.role] ??= entry.definition.build(host);
}
const result = await definition.run(ctx);

Load a definition, parse its params, make a host, build each adapter onto ctx under its role, await run. The ??= is the earlier-wins rule: the first adapter found for a role keeps it.

This runner uses only the starter catalog, so it never scans the project or home catalogs and ignores the defaults file. A real frontend calls installed(cwd) and pick(...) instead.

Catalogs

A catalog is a folder with workflows/ and adapters/ inside it. roots(cwd) returns the ones to scan, in order, and earlier wins.

Scope Folder For
project <cwd>/.penguin Definitions that belong to this repository
home ~/.penguin Yours, everywhere
catalog Each line of ~/.penguin/catalogs, resolved against ~/.penguin Shared or vendored sets
starter The engine package's examples/ The line starter in the catalogs file

The catalogs file is one path per line. Blank lines and # comments are skipped, and a line pointing at a folder that does not exist is skipped rather than reported. The word starter is special: it resolves to the engine's own examples/ directory, wherever the package is installed.

installed(cwd) scans adapters/ in every root, imports each .ts file that is not a .d.ts, and drops duplicates by role plus name, so a project vcs/git shadows a home one. The scan is eager because role and name live in the module, not the filename.

Workflows are cheaper. found(cwd) lists the .ts files in every workflows/ folder without importing anything, and the name is the filename minus the extension. locate(name, cwd) returns the first match. searchedWorkflows(cwd) and searchedAdapters(cwd) return the folders that were scanned, so a frontend can say where it looked when it found nothing.

Picking an implementation

pick(list, role, name?) resolves one implementation and answers with a tagged result rather than throwing: 

export type Picked = { found: AdapterFound } | { missing: string } | { conflict: string };

It tries an explicit name, then the role's line in ~/.penguin/defaults, then the only implementation when there is exactly one. With more than one and no choice recorded, it names them and says how to fix it:

2 vcs adapters are installed (git, jj).
Write "vcs jj" to /Users/you/.penguin/defaults to choose one.

The defaults file is one role name pair per line, with the same blank-and-comment handling as the catalogs file.

Where the folders come from

packages/engine/src/paths.ts is the only place that answers this.

Function Default Override
home() ~/.penguin PENGUIN_HOME
stateRoot() ~/.local/state/penguin XDG_STATE_HOME
projectHome(cwd) <cwd>/.penguin none
defaultsFile() ~/.penguin/defaults follows home()
catalogsFile() ~/.penguin/catalogs follows home()

Both environment overrides are ignored when empty, and both resolve to absolute paths.

Loading a definition file

A workflow file imports penguin and zod as bare specifiers, and there is no node_modules next to it. Asking a person to run bun install in every folder that holds a definition is a chore, so src/catalog/loader.ts registers one Bun plugin, once per process, that serves both names from Penguin's own copies: 

Bun.plugin({
  name: "penguin-definitions",
  setup(build) {
    build.module("penguin", async () => ({
      exports: { ...(await import("../core/index.ts")) },
      loader: "object",
    }));
    build.module("zod", () => ({ exports: { ...zod }, loader: "object" }));
  },
});
  • A definition file gets exactly the zod Penguin is using, so a schema built in a workflow and parsed by the engine come from the same library.
  • It works inside a compiled binary, where neither module exists on disk. That is why the plugin serves objects rather than file paths.
  • zod is imported statically at the top of the loader. A dynamic import("zod") would resolve back through this same plugin and hang.

importDefault resolves the path to absolute and converts it to a file:// URL, because a bare relative path in a dynamic import resolves against the importing module rather than the process. load(file) and loadAdapter(file) then duck-type what came back and throw PenguinError naming the file when it does not fit: 

throw new PenguinError(`${file} does not default-export a workflow`);
throw new PenguinError(`${file} has no description`);

The checks are duck-typed, not instanceof. The file was imported through a plugin into a fresh module graph, so identity checks would be the wrong tool.

Errors

export class PenguinError extends Error {}

export function messageOf(error: unknown): string {
  if (error instanceof Error) return error.message;
  return String(error);
}

PenguinError means Penguin itself is refusing: a workflow with no description, an adapter missing a field, a file that does not default-export what it claims. messageOf lets a frontend print a caught unknown without a type dance.
