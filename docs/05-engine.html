The engine

The engine does five things every time a workflow runs.

Job Means Code
Catalog Find workflow and adapter files across catalog directories src/catalog/
Ctx Validate params and wire installed adapter roles onto ctx src/run.ts
Process Own the run's working directory and the processes it spawns src/host.ts
Run file Append the run's whole story to its file, the state every frontend reads src/trace.ts
Sub-runs Spawn each call as its own process with its own run file src/run.ts, src/child.ts

What it refuses

  • It does not route messages. A promise already goes back to its caller.
  • It does not hold state machines. A workflow is TypeScript control flow.
  • It does not retry agent turns. The agent adapters do, because retry is CLI-shaped.
  • It does not render anything. The view adapter does.
  • It does not know one adapter role from another. vcs, agent, and view are strings to it. It builds every installed adapter against the same host and puts the result on ctx under its role, with no idea that view is special.

The test for a new feature. If a proposal needs a fourth engine job, a new base class, or a new lifecycle hook, it is in the wrong place. It is either a new adapter, a new workflow, or out of scope.

The whole runtime path

run(file, params, options) in src/run.ts is the engine's one wiring function, exported as penguin/run. Its whole body: 

const definition = await load(file);
const parsed = definition.params.parse(params);
const trace = createTrace({ id, workflow: file, params: parsed, cwd, root, parent });
const host = createHost(cwd, { id, dir: trace.dir }, list);
const found = await installedIn(list);
for (const role of new Set(found.map((entry) => entry.role))) {
  const picked = pick(found, role);
  if ("missing" in picked) throw new PenguinError(picked.missing);
  if ("conflict" in picked) throw new PenguinError(picked.conflict);
  ctx[role] = trace.wrap(role, picked.found.definition.build(host));
}
return definition.run(ctx);

Load a definition, parse its params, open the run file, make a host, resolve one implementation per role through pick, build it onto ctx, await run. Ambiguity is reported, never guessed: a role with two installed implementations and no recorded choice refuses to run and names the file to edit, except a builtin, which any single installed implementation shadows. Each built adapter is wrapped by the run file on the way in, so every call it receives lands there.

run also puts one hook on ctx for call: spawning a child workflow as its own process, bun src/child.ts, with its own id, its own run folder, and this run recorded as its parent. The parent's file notes the child's id, and the child's outcome, throw, or stop comes back to the awaiting call from the child's own file. Stopping a run is killing its process group; each child is its own group, so stopping a subtree is walking the head-line pids and killing each.

examples/run.ts is a frontend the way every frontend is one: it claims a run id, calls run, then tails the run folders, prints shows, presents asks, and appends answers and messages to inboxes. A daemon or a UI does the same with different rendering.

The run file

Each run owns ~/.local/state/penguin/runs/<id>/, holding two files. run.jsonl is written by the run: a head line with the run's id, pid, workflow, params, cwd, git root, and parent; a pending line when a call starts and a line with its outcome and elapsedMs when it settles, the two sharing an id; a note per spawned child; a {"dir": ...} note when the run moves its work into a worktree; and the final result, error, or stop. Values are recorded whole, with a zod shape written as its JSON Schema so a frontend can render the control an ask needs. A call that returns a live object (an open stream, a turn) is marked handle: true instead, since an object like that cannot be written down. One frontend note is allowed in: a {"name": ...} line renames the run, the newest winning. Every writer appends whole single lines, which is what keeps two writers safe.

inbox.jsonl is the run's one way in, appended by frontends: {"answer": ...} settles the oldest pending ask, {"message": "..."} reaches every listener. Everything else about a run is derived by reading: running is a live pid, blocked is a pending ask with no outcome, done, failed, and stopped are the closing note, and crashed is a dead pid with no closing note. No state lives anywhere else, which is why any frontend can quit at any time and nothing changes.

The run file is also the resume journal. run(file, params, { resume }) takes a prior run file: each call that matches the next recorded one hands back the recorded outcome without calling out, and the run goes live at the first call the file does not hold, a mismatch, a throw, or a handle. From there every call runs for real. latestRun() names the newest file.

Catalogs

A catalog is a folder with workflows/, adapters/, and skills/ inside it. roots(cwd) returns the ones to scan, in order, and earlier wins.

Scope Folder For
project <cwd>/.penguin Definitions that belong to this repository
home ~/.penguin Yours, everywhere
catalog Each line of ~/.penguin/catalogs, resolved against ~/.penguin Shared or vendored sets
starter The engine package's examples/ The line starter in the catalogs file
worktree The .penguin of every other checkout of cwd's repository Definitions written on a branch, before they merge
builtin The engine package's src/adapters/ Always last: the files view, shadowed by anything installed

The catalogs file is one path per line. Blank lines and # comments are skipped, and a line pointing at a folder that does not exist is skipped rather than reported. The word starter is special: it resolves to the engine's own examples/ directory, wherever the package is installed.

Worktree catalogs are read from .git/worktrees/, with no git subprocess, so the main checkout sees every branch and a branch sees the main checkout and its siblings. A checkout with no .penguin folder is skipped, and cwd's own catalog is never listed twice. A branch may only add a name, never take one over: a worktree adapter is dropped unless it is the one and only claim on its role, and a worktree skill is dropped when any other catalog supplies that name. Workflows list one row per file, so a branch's ship appears beside the project's, and the run's directory stays the project it started from.

installed(cwd) scans adapters/ in every root, imports each .ts file that is not a .d.ts, and drops duplicates by role plus name, so a project vcs/git shadows a home one. The scan is eager because role and name live in the module, not the filename.

Workflows are cheaper. found(cwd) lists the .ts files in every workflows/ folder without importing anything, and the name is the filename minus the extension. locate(name, cwd) returns the first match. searchedWorkflows(cwd) and searchedAdapters(cwd) return the folders that were scanned, so a frontend can say where it looked when it found nothing.

Picking an implementation

pick(list, role, name?) resolves one implementation and answers with a tagged result rather than throwing: 

export type Picked = { found: AdapterFound } | { missing: string } | { conflict: string };

It tries an explicit name, then the role's line in ~/.penguin/config, then the only installed implementation, a builtin counting only when nothing shadows it. With more than one and no choice recorded, it names them and says how to fix it:

2 vcs adapters are installed (git, jj).
Write "vcs jj" to /Users/you/.penguin/config to choose one.

The config file is one key value pair per line, with the same blank-and-comment handling as the catalogs file. A role line picks an adapter; other keys are settings, like worktrees for where the git adapter puts them.

Where the folders come from

packages/engine/src/paths.ts is the only place that answers this.

Function Default Override
home() ~/.penguin PENGUIN_HOME
stateRoot() ~/.local/state/penguin XDG_STATE_HOME
projectHome(cwd) <cwd>/.penguin none
runsDir() ~/.local/state/penguin/runs follows stateRoot()
configFile() ~/.penguin/config follows home()
catalogsFile() ~/.penguin/catalogs follows home()

Both environment overrides are ignored when empty, and both resolve to absolute paths.

Loading a definition file

A workflow file imports penguin and zod as bare specifiers, and there is no node_modules next to it. Asking a person to run bun install in every folder that holds a definition is a chore, so src/catalog/loader.ts registers one Bun plugin, once per process, that serves both names from Penguin's own copies: 

Bun.plugin({
  name: "penguin-definitions",
  setup(build) {
    build.module("penguin", async () => ({
      exports: { ...(await import("../core/index.ts")) },
      loader: "object",
    }));
    build.module("zod", () => ({ exports: { ...zod }, loader: "object" }));
  },
});
  • A definition file gets exactly the zod Penguin is using, so a schema built in a workflow and parsed by the engine come from the same library.
  • It works inside a compiled binary, where neither module exists on disk. That is why the plugin serves objects rather than file paths.
  • zod is imported statically at the top of the loader. A dynamic import("zod") would resolve back through this same plugin and hang.

importDefault resolves the path to absolute and converts it to a file:// URL, because a bare relative path in a dynamic import resolves against the importing module rather than the process. load(file) and loadAdapter(file) then duck-type what came back and throw PenguinError naming the file when it does not fit: 

throw new PenguinError(`${file} does not default-export a workflow`);
throw new PenguinError(`${file} has no description`);

The checks are duck-typed, not instanceof. The file was imported through a plugin into a fresh module graph, so identity checks would be the wrong tool.

Errors

export class PenguinError extends Error {}
export class RunStopped extends PenguinError {}
export class RunCrashed extends PenguinError {}

export function messageOf(error: unknown): string {
  if (error instanceof Error) return error.message;
  return String(error);
}

PenguinError means Penguin itself is refusing: a workflow with no description, an adapter missing a field, a file that does not default-export what it claims. RunStopped and RunCrashed are how a parent's call rejects when a child was stopped or died without recording an outcome, so a workflow can catch exactly those. messageOf lets a frontend print a caught unknown without a type dance.
