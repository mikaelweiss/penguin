Adapters

An adapter connects workflows to exactly one outside thing. It is a role, a name, a description, and a build(host) that returns the functions a workflow calls through ctx.<role>. Put a .ts file in a catalog's adapters/ folder, default-export an adapter(...), and every workflow can reach it. 

import { adapter } from "penguin";

export default adapter({
  role: "vcs",
  name: "git",
  description: "git working copies",
  build: (host) => ({
    async commit(message: string, options?: { cwd?: string }) {
      const done = await host.shell(`git commit -m ${quoted(message)}`, { cwd: options?.cwd });
      return { ok: done.code === 0, reason: (done.stdout + done.stderr).trim() };
    },
  }),
});

adapter() checks that role, name, and description are non-blank strings and that build is a function, then hands the object back untouched. build runs once per run. Anything the adapter remembers for the length of a run is a closure variable, which is how the claude adapter keeps its session map.

Pick the role first

The role is the contract every workflow codes against, so choose it before the API. Reuse an existing role when your thing plays the same part: a jj adapter is role: "vcs", and it inherits every workflow written for git. Invent a role only for a genuinely new outside thing.

The two rules

Functions carry plain data

An adapter function takes and returns JSON-serializable values, or an async stream of them. Never functions, never objects with methods. A frontend on the other side of a socket has to see the same values a terminal sees.

Data for expected outcomes, a throw when the bridge broke

A failed commit is a normal thing that happens, so it comes back as { ok: false, reason } for the workflow to handle. A throw means the adapter could not do its job at all. The claude adapter throws when you pass a session id it never opened, because there is no sensible { ok: false } for a caller mistake: 

if (opened === undefined) {
  throw new PenguinError(`no open session ${session}. ctx.agent.open() gives one.`);
}

Include the fix in the message. A person reads it.

What an adapter cannot do

  • Write to the view. It has no view.
  • Ask a person anything.
  • Call another adapter.
  • Touch anything outside host.

An adapter that wants to narrate returns the words and lets the workflow decide. The claude adapter returns a stream of chunks. Whether any of it reaches a screen is the workflow's call.

The host

host is everything an adapter is allowed to touch. Four members, no way past them.

export type Host = {
  cwd: string;
  state: string;
  shell(cmd: string, options?: ShellOptions): Promise<CommandResult>;
  exec(argv: string[], options?: ExecOptions): Promise<number>;
};

cwd is the folder the run was invoked from, and relative cwd options on adapter calls resolve against it. state is where an adapter puts what it keeps between runs, which is why git worktrees land at <state>/worktrees/<project>/<name> instead of inside the repository. Without state, every adapter would invent its own hidden folder.

shell(cmd) exec(argv)
Input One string, run through a real shell An argv array, spawned directly
Returns { code, stdout, stderr } when the process closes The exit code
Output Buffered whole Streamed through onOutput(chunk, stream)
Use for Short commands whose output you read at the end Long commands you want to watch, and untrusted arguments

Both accept cwd and stdin. When stdin is undefined the child's stdin is ignored; when it is a string, the string is written and the pipe closed. Errors on that pipe are swallowed, because a process that exits before reading its input is normal, not a crash.

The git adapter is all shell: git status --porcelain returns quickly and the caller wants the text. The claude adapter is all exec: the CLI runs for minutes and the adapter parses stream-json line by line as it arrives.

Quote everything you interpolate. host.shell runs a real shell. The git adapter wraps every interpolated value in its own quoted() helper, which single-quotes and escapes embedded quotes. When the values come from a person or an agent, prefer host.exec with an argv array. Nothing is parsed, so nothing can be injected. 

function quoted(text: string): string {
  return `'${text.replaceAll("'", "'\\''")}'`;
}

await host.shell(`git add -- ${files.map(quoted).join(" ")}`, { cwd: options?.cwd });

Chaining inside one shell call is fine. vcs.pull runs git fetch origin <ref> && git reset --hard FETCH_HEAD in a single call, so there is one outcome and no half-done state to report.

Conventions worth copying

Nothing in the engine requires these. The starter catalog is consistent about them.

  • Every result carries ok and reason, so a failure always has something to show.
  • Extra facts ride alongside rather than replacing them: dirty returns { ok, dirty, reason }, head returns { ok, branch, sha, detached, reason }.
  • cwd is an option on each call, not state on the adapter, so one adapter serves many folders in one run. An adapter that stored a folder at build time could not run commit-all.
  • Related calls nest under a plain object: vcs.branch.create, vcs.rebase.onto, vcs.worktree.add. Still plain data in and out.
  • Ambiguity is reported, not guessed. defaultBranch reads refs/remotes/origin/HEAD and answers ok: false when it is unset, rather than assuming main. worktree.add answers { ok: false, exists: true } when the target folder is already there, so the workflow chooses between reusing it and failing.

Streaming

When the outside thing keeps talking, return an AsyncIterable. There is no engine support to opt into. The claude adapter's whole streaming machinery is one small class: 

class Channel<T> implements AsyncIterable<T> {
  private items: T[] = [];
  private waiters: ((result: IteratorResult<T>) => void)[] = [];
  private done = false;

  push(item: T): void { /* hand to a waiter, or buffer */ }
  end(): void { /* resolve every waiter as done */ }
  [Symbol.asyncIterator](): AsyncIterator<T> { /* drain, then wait */ }
}

End the channel in a finally so a consumer's for await cannot hang when the work throws.

Register the types

Add the role to the Adapters interface so workflows type-check. In the starter catalog that is examples/penguin-env.d.ts, maintained by hand: 

declare module "penguin" {
  interface Adapters {
    vcs: ReturnType<(typeof git)["build"]>;
  }
}

ReturnType<typeof build> rather than a hand-written interface. The implementation is the contract, and there is nothing to keep in sync.

What lives in the implementation, not the model

The terminal view in examples/adapters/view.ts solves two problems that belong to terminals alone. stdin is a single resource, so it appends each question to a promise chain and prompts one at a time. The workflow still sees two independent promises, and a web view that can ask both at once would not need the code.

A person answering also types a line, so when the shape wants a number, a list, or an object, the adapter tries the raw text and its JSON.parse before giving up. A bad answer is not an error: it prints what did not fit and asks again until the answer parses.

Two implementations of one role

Ship a second name under the same role and both are installed. Penguin will not choose between them. It reports the conflict and names the file to edit. See The engine.
