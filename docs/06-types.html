Reading the types

penguin uses a handful of TypeScript mechanisms that read strangely if TypeScript is not your first language. Each one is listed here once, with the file that uses it. After these six, nothing in the codebase should look like magic.

Types are shapes, not declarations

In most typed languages a value has a type because you declared the relationship, the way a Swift type conforms to a protocol with : Adapter. TypeScript checks shape instead: anything with the right fields is the type. That is why workflow() in src/core/workflow.ts takes a plain object literal and hands it back. No class, no conformance, no registration. The object has description, params, and run, so it is a Workflow. Half the codebase stops looking strange once this clicks.

Objects of closures instead of classes

Where another language reaches for a class with stored properties, TypeScript idiom returns an object literal full of functions that close over what they need. examples/adapters/git.ts is one build(host) returning an object of async functions, each closing over host. Same capability as a class, less ceremony, and nothing to instantiate.

zod exists because the types vanish at runtime

TypeScript types are erased when the code runs, so nothing checks that JSON from the outside actually has the declared shape. Zod is the runtime half: z.object({...}) is a value that can validate, and z.infer<typeof Schema> derives the compile-time type from it, so the shape is written once and both worlds agree. Every params schema, every ask shape, and every agent result shape in penguin is this one pattern.

Union types are enums with payloads

Picked in src/catalog/adapters.ts reads { found } | { missing } | { conflict }: a value is exactly one of the three, and checking which one ("found" in picked) narrows the type. If you know Swift enums with associated values, this is that. Reading | as "one of these cases" makes most TypeScript signatures legible.

Declaration merging is how ctx gets its type

The core declares an empty interface Adapters {}. A catalog widens it from outside, in examples/penguin-env.d.ts, by declaring the same interface inside declare module "penguin": TypeScript merges the two declarations, and ctx.vcs is suddenly typed everywhere. SwiftUI does the identical thing when you extend EnvironmentValues with your own keys. The ReturnType<(typeof git)["build"]> in that file means "whatever build actually returns", so the implementation is the contract and there is nothing to keep in sync.

The one real piece of magic

Definition files import penguin and zod with no install of their own. src/catalog/loader.ts registers a Bun plugin that serves both names from penguin's own copies, which is ten lines and the only place in the codebase where something happens that plain reading would not predict. Everything else is functions calling functions.
