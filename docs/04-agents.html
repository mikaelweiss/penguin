Agents

An agent CLI is one more outside thing, so it is one more adapter, role agent. The engine has no idea agents exist. No part of it retries a turn, parses a model's output, or holds a conversation.

The API

const session = await agent.open();
const turn = agent.turn(session, { skill: "commit" }, { result: Commit });
for await (const chunk of turn.output) await view.show(chunk.text);
const commit = await turn.value;
  • open(options) returns a session id. A session is one conversation: the first turn opens it, later turns resume it.
  • turn(session, ask) returns a handle with two halves. output is an AsyncIterable of what the agent is doing. value is a promise of the result.
  • ask is { skill, prompt? } or a prompt string. A skill carries the reusable instructions; the prompt carries the dynamic part.
  • Pass { result: Shape } and value is typed as z.infer<Shape>. Without it, value resolves to null.
  • stop(session) ends the running turn. The session survives, so the next turn can correct course.

Splitting output from value is the design. The stream is what happened, the value is what it produced, and the workflow decides whether the stream reaches a person.

Choosing model capacity

A workflow can open a session with { model: "small" }, { model: "normal" }, or { model: "big" }. These names state how much model the work needs without naming a provider. A session that names none runs on normal, so a workflow spells out only the turns that take more or less than ordinary work. The adapter translates the choice:

Choice claude codex copilot
smallsonnetgpt-5.6-terraclaude-haiku-4.5
normalopusgpt-5.6-solclaude-sonnet-4.6
bigfablegpt-5.6-solgpt-5.3-codex

Exact model names still pass through unchanged, which is the only way a run reaches a model no tier maps to. No claude tier maps to fable: it costs twice what opus does per token, so it is reached only by name or by a claude-big-model fable config line. A direct-provider adapter has the defaults above. A multi-provider adapter falls back to its own default model unless a config line maps the choice, such as opencode-normal-model openai/gpt-5.6-sol. The key is always <adapter>-<choice>-model. The same key overrides a direct-provider default, so a model update does not require editing a workflow.

Skills

Instructions an agent reuses live as skills, never as prose in workflow code. A skill is a folder under a catalog's skills/ holding a SKILL.md in the Agent Skills format: name and description frontmatter, the instructions below, extra files beside it. The name must match the folder. The starter catalog's skills/commit/ is the model.

A turn takes { skill: "commit" } in place of a prompt string. The adapter resolves the name through host.skill(), which searches the run's catalogs in order, project first, so a project can shadow a shared skill. The adapter sends the skill's body, then where the skill's files live when it has any, then the prompt. That prompt is for runtime data only: the branch name, the file list, what a person typed. A prompt string alone stays right when the whole ask is runtime data: a user's words forwarded mid-conversation.

The line to hold: if the text would be the same on every run, it is a skill. If it exists only at run time, it is a prompt.

Chunks

type Chunk = { kind: "text" | "thinking" | "tool"; text: string; detail?: string };

For a tool call, text is the tool name and detail is the one value that says what it acts on. The claude adapter picks that value by looking for a known field, in order: command, file_path, path, pattern, query, url, skill, description, prompt, then the first non-empty string in the input. Only the adapter knows a particular CLI's tool shapes, and that knowledge stays there.

The workflow chooses what to show, and formats it here rather than in the adapter:

for await (const chunk of turn.output) {
  if (chunk.kind === "text") await view.show(chunk.text);
  if (chunk.kind === "tool") await view.show(`  ${chunk.text}: ${chunk.detail ?? ""}`);
}

Thinking is dropped here. Another workflow could show it. The starter workflows share this loop as narrate and narrated in examples/helpers/turns.ts.

Typed results

Give the turn a Zod object and the adapter converts it to JSON Schema, hands it to the CLI as --json-schema, and validates what comes back. A turn that ends in a typed value is what makes "the agent is done" a fact rather than a guess. 

const Commit = z.object({
  files: z.array(z.string()).describe("the paths to commit, as git status prints them"),
  message: z.string().describe("the commit message, the title on the first line"),
});

The .describe() calls survive into the JSON Schema, so they are prompt text the model sees at the point it fills each field.

Retry lives in the catalog

A turn runs at most twice. When the first attempt fails, whether the CLI exited non-zero, reported an error, returned no structured output, or returned something the schema rejected, the session machinery every agent adapter shares, sessions() in examples/helpers/turns.ts, reruns the prompt with a correction appended: 

const sent = failure === undefined
  ? prompt
  : `${prompt}\n\n# Correction\n\nThe last attempt failed: ${failure}\nDo the turn again and fix that.`;

After two failures it throws PenguinError. That is the bridge admitting it could not do its job, which is what a throw is for.

Instructions every session gets

What every agent should hear, whichever CLI runs it, goes in ~/.penguin/instructions.md. The engine sends it ahead of the prompt on each session's first turn, after a skill's own body when the turn runs one. A CLI's own instruction files (a CLAUDE.md, say) reach only that CLI, so this is where a rule for all of them lives. Nothing is sent when the file is absent.

A usage limit waits, it does not fail

A usage limit is not a mistake the agent can correct, so correcting it wastes the one retry and the run dies on a wall that clears itself. An adapter marks that failure instead: 

return { ok: false, error: "You've hit your session limit · resets 3pm", limited: true };

sessions() then parks the turn rather than counting it as a try. It notes the pause to the run file, sleeps limit-wait-seconds from ~/.penguin/config (120 by default), and sends the same prompt again on the same session, for as long as the limit holds. Stopping the run still ends a parked turn, and the penguin app shows it as waiting, with the agent's own sentence about when the limit resets.

Stopping a turn

A turn runs a child process until it finishes, and sometimes the workflow learns mid-flight that it should not: a person sent a message, a PR closed, a watch stream fired. agent.stop(session) kills the running process; the awaited turn.value then rejects with "the turn was stopped", and the session stays open for a corrective turn. examples/workflows/review-pr.ts races the PR's change stream against turn.value, stops the reviewer when the PR closes, goes to draft, or gains new code, and resumes the same session with what changed.

How the claude adapter drives the CLI

One CLI process serves a session. The first turn starts it and every later turn goes down the same stdin, so the CLI builds its prompt once and the API's cache holds across turns. Restarting a process per turn, the old way, rewrote the whole conversation into cache at three out of four turn boundaries, at the write rate.

Flag Why
--input-format stream-json --output-format stream-json --verbose Prompts go in as line-delimited user messages and events come out the same way, so one process takes many turns and output emits while a turn runs.
--session-id then --resume The first process of a session names it. A process that ended, was stopped, or held a different result schema is replaced by one that resumes the same id.
--json-schema Only when the turn asked for a typed result. The result tool is fixed when the process starts, so a turn with a different schema starts a new process.
--permission-mode bypassPermissions A run has no one to ask, so a denied edit costs the turn. The permission option overrides it.
CLAUDE_CODE_PROMPT_CACHE_TTL=5m in the environment Turns sit seconds apart, so the five minute cache tier holds and its writes cost less than the CLI's one hour default. claude-cache-ttl in ~/.penguin/config overrides it.

Each turn's line is {"type": "user", "message": {"role": "user", "content": ...}}. Output is buffered by line, parsed, and pushed into a Channel until the turn's result event. A run that ends kills its processes, so no agent outlives it.

What a turn costs

After every attempt, sessions() writes one note to the run file with what the CLI reported it spent: 

{"at": "...", "usage": {"adapter": "claude", "session": "...", "skill": "review",
  "model": "claude-opus-5", "input": 12, "cacheRead": 118400, "cacheWrite": 2100,
  "output": 380, "usd": 0.0421}}

Tokens are the turn's own. usd is set when the CLI priced the turn (claude, opencode, pi) or when a price-<model> line in ~/.penguin/config holds the model's input, cached input, and output dollars per million tokens, as in price-gpt-5.6-sol 2,0.5,10 (codex, cursor, through examples/helpers/prices.ts). A failed attempt is noted too, since its tokens were spent, so a corrected retry shows as two notes. An adapter whose CLI reports nothing writes nothing (copilot), and a reader takes a missing note as unknown, never as free. The penguin app sums the notes per run and per tree, and bun examples/cost.ts lists runs with their cost, which is how a change to a skill or an adapter is checked against the runs before it.

Swapping the agent

The starter catalog ships six: claude, copilot, codex, cursor, opencode, and pi, all role agent. Each one is a runOnce, one CLI invocation that streams chunks and reports how it ended, handed to the shared sessions() in examples/helpers/turns.ts, which owns opening, retry, schema checks, and stop. Write agent <name> to ~/.penguin/config to choose one. Your own harness is one more runOnce, and no workflow changes.

A session on another agent

One run is not held to one CLI. A session names the adapter it wants, and ctx.agent routes on that name, remembering which adapter owns the id it handed back so the session's later turns and its stop reach the CLI holding the conversation: 

const reviewer = await agent.open({ adapter: "cursor", model: "big" });

The starter catalog spends this on code review: review.ts, the reviewer in implement.ts, the gatherer in review-pr.ts, and the reviewer in make-workflow.ts all open on REVIEWER from examples/helpers/models.ts, so the change is read by a CLI other than the one that wrote it. The sessions that write code, and the judge in review-pr.ts whose whole design is that it holds no tools, stay on the configured adapter.

An adapter nobody installed, one whose check() objects, or one that will not build is not worth ending a run over: the session opens on the configured adapter instead and the run file records a fallback note saying what was wanted, what ran, and why. Only the configured adapter is preflighted, so a cursor nobody logged into never blocks a run that never asks for it. An adapter takes only the options it knows: cursor reads cwd and model, and drops the rest.
