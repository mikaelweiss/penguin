Agents

An agent CLI is one more outside thing, so it is one more adapter, role agent. The engine has no idea agents exist. No part of it retries a turn, parses a model's output, or holds a conversation.

The API

const session = await agent.open({ cwd: params.dir });
const turn = agent.turn(session, { skill: "commit" }, { result: Commit });
for await (const chunk of turn.output) await view.show(chunk.text);
const commit = await turn.value;
  • open(options) returns a session id. A session is one conversation: the first turn opens it, later turns resume it.
  • turn(session, ask) returns a handle with two halves. output is an AsyncIterable of what the agent is doing. value is a promise of the result.
  • ask is { skill, prompt? } or a prompt string. A skill carries the reusable instructions; the prompt carries the dynamic part.
  • Pass { result: Shape } and value is typed as z.infer<Shape>. Without it, value resolves to null.
  • stop(session) ends the running turn. The session survives, so the next turn can correct course.

Splitting output from value is the design. The stream is what happened, the value is what it produced, and the workflow decides whether the stream reaches a person.

Skills

Instructions an agent reuses live as skills, never as prose in workflow code. A skill is a folder under a catalog's skills/ holding a SKILL.md in the Agent Skills format: name and description frontmatter, the instructions below, extra files beside it. The name must match the folder. The starter catalog's skills/commit/ is the model.

A turn takes { skill: "commit" } in place of a prompt string. The adapter resolves the name through host.skill(), which searches the run's catalogs in order, project first, so a project can shadow a shared skill. The adapter sends the skill's body, then where the skill's files live when it has any, then the prompt. That prompt is for runtime data only: the branch name, the file list, what a person typed. A prompt string alone stays right when the whole ask is runtime data, the way steer forwards a user's words.

The line to hold: if the text would be the same on every run, it is a skill. If it exists only at run time, it is a prompt.

Chunks

type Chunk = { kind: "text" | "thinking" | "tool"; text: string; detail?: string };

For a tool call, text is the tool name and detail is the one value that says what it acts on. The claude adapter picks that value by looking for a known field, in order: command, file_path, path, pattern, query, url, skill, description, prompt, then the first non-empty string in the input. Only the adapter knows a particular CLI's tool shapes, and that knowledge stays there.

The workflow chooses what to show, and formats it here rather than in the adapter:

for await (const chunk of turn.output) {
  if (chunk.kind === "text") await view.show(chunk.text);
  if (chunk.kind === "tool") await view.show(`  ${chunk.text}: ${chunk.detail ?? ""}`);
}

Thinking is dropped here. Another workflow could show it.

Typed results

Give the turn a Zod object and the adapter converts it to JSON Schema, hands it to the CLI as --json-schema, and validates what comes back. A turn that ends in a typed value is what makes "the agent is done" a fact rather than a guess. 

const Commit = z.object({
  files: z.array(z.string()).describe("the paths to commit, as git status prints them"),
  message: z.string().describe("the commit message, the title on the first line"),
});

The .describe() calls survive into the JSON Schema, so they are prompt text the model sees at the point it fills each field.

Retry lives in the adapter

A turn runs at most twice. When the first attempt fails, whether the CLI exited non-zero, reported an error, returned no structured output, or returned something the schema rejected, the adapter reruns the prompt with a correction appended: 

const sent = failure === undefined
  ? prompt
  : `${prompt}\n\n# Correction\n\nThe last attempt failed: ${failure}\nDo the turn again and fix that.`;

After two failures it throws PenguinError. That is the bridge admitting it could not do its job, which is what a throw is for.

Stopping a turn

A turn runs a child process until it finishes, and sometimes the workflow learns mid-flight that it should not: a person sent a message, a PR closed, a watch stream fired. agent.stop(session) kills the running process; the awaited turn.value then rejects with "the turn was stopped", and the session stays open for a corrective turn. examples/workflows/steer.ts races view.listen() against turn.value and stops on the first message, which is the whole pause-and-steer pattern in one file.

How the claude adapter drives the CLI

Flag Why
--output-format stream-json --verbose Line-delimited events, so output can emit while the turn runs.
--session-id then --resume The adapter tracks which sessions have started and picks the right one.
--json-schema Only when the turn asked for a typed result.
--permission-mode acceptEdits A run has no one to ask, so a denied edit costs the turn. The permission option overrides it.

The prompt goes in on stdin. Output is buffered by line, parsed, and pushed into a Channel.

Swapping the agent

Codex, Gemini, or your own harness is another adapter with role agent and a different name. As long as it answers open and turn, no workflow changes.
